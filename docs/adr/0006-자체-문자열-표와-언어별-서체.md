# 언어 전환은 자체 문자열 표(`Loc`)와 언어별 TMP 서체로 한다

한국어·일본어 두 언어를 코드 안의 표 하나(`Loc`)로 전환한다. Unity Localization 패키지는 쓰지 않는다. 서체는 언어마다 Noto Sans KR/JP 동적 TMP 아틀라스를 따로 두고 서로를 fallback으로 건다.

## 결정

- **문자열**: `Loc.cs`의 표가 키마다 {한국어, 일본어}를 가진다. 현재 언어는 `SettingsData.language`(정수 enum, 기본 한국어)에 저장한다. 없는 키는 키 문자열을 그대로 보이고 경고를 남긴다.
- **즉시 반영**: 모든 TMP 라벨에 `LocText`가 붙는다(`UiKit.NewLabel`이 자동으로 붙임). `Loc.Set`이 `Changed`를 알리면 열려 있는 라벨이 문자열과 서체를 다시 채운다. 화면 재생성이 필요 없다.
- **서체**: `UiTheme.Font`가 현재 언어의 서체를 돌려준다. 한국어 서체 ↔ 일본어 서체가 서로 fallback이라 언어 선택 칩의 "한국어"·"日本語"가 어느 모드에서도 깨지지 않는다.
- 새 화면(갤러리 등)은 표에 키를 더하고 `Loc.Get`과 `LocText.Key`로 쓴다.

## Considered Options

- **Unity Localization 패키지**: 이 규모(두 언어, 문자열 수십~수백 개)에는 과하다. 에셋 테이블·로케일 에셋·Addressables 의존이 생기고, 테스트가 어렵다. 반대로 Smart Format·복수형·에셋 로컬라이즈(이미지·음성)가 필요해지면 이 결정을 다시 본다.
- **언어마다 폰트 하나로 합친 통합 아틀라스**: 한·일 한자 자형이 달라서(같은 코드 포인트에 지역별 자형) 언어별 서체가 낫다.
- **정적 아틀라스(글리프 미리 굽기)**: 대본이 아직 없어 쓸 글자를 모른다. 동적 아틀라스는 쓰는 글자만 런타임에 채운다.

## Consequences

- 대사·이벤트 텍스트는 양이 많아지면 코드 표가 아니라 별도 데이터 파일(CSV/JSON)로 옮겨야 한다. 그때도 `Loc.Get(key)` 인터페이스는 유지할 수 있다.
- 한국어 문자열을 추가하면 일본어도 같이 써야 한다(`LanguageTests`가 빈 칸을 잡는다).
- 일본어 번역문은 기계적 초안이다. 출시 전 원어민 검수가 필요하다.
- 동적 아틀라스는 첫 표시 때 글리프를 만드느라 한 프레임 걸릴 수 있다. 아틀라스 크기(1024)는 대본이 늘면 다시 확인한다.
